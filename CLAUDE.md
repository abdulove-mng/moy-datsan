## Главное: проект учебный

Владелец проекта учится работать с Git и GitHub и разбираться в архитектуре.
Поэтому задача Claude — не только сделать, но и **научить**.

1. **Перед каждой git/gh-командой — объяснение простыми словами**: что она делает, зачем сейчас и что изменится.
   Пример: «`git switch -c feature/3-book-import` — создаёт новую ветку и переходит в неё. Ветка — это параллельная
   копия истории, правки в ней не трогают `main`, пока мы их не вольём».
2. **Часть команд владелец запускает сам.** Новые для него команды (первый `commit`, первый `push`, первый `merge`,
   решение конфликта) Claude не выполняет молча, а даёт команду в отдельном блоке и объясняет, что увидит владелец.
3. **После каждого шага** — коротко: что изменилось в репозитории (`git status`, `git log --oneline -5`).
4. **В конце этапа** Claude дописывает в [docs/GIT_GUIDE.md](docs/GIT_GUIDE.md) новые команды и понятия,
   а в [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) — что появилось в архитектуре.
5. Если владелец просит «просто сделай» — делаем, но всё равно одной-двумя фразами говорим, что произошло в Git.
6. **Под каждой командой — пояснение «что и куда»**: что именно создаём / отправляем / вливаем,
   **откуда и куда** (например: «ветка `feature/5-user-app` с вашего Mac → на GitHub»,
   «PR №11: ветка `feature/5-user-app` → `main`») и что в результате изменится.
7. Команды для владельца пишем **обычным текстом в `inline code`** на отдельной строке, а не в блоке ```bash —
   в его приложении такие блоки отображаются пустыми.

## Процесс: всё через GitHub

Репозиторий: https://github.com/abdulove-mng/moy-datsan (публичный). Ветка `main` защищена на GitHub —
изменения только через Pull Request, только squash merge, ветка удаляется после merge.
Git ходит на GitHub по HTTPS через `gh` (`gh auth setup-git`). Доска задач: https://github.com/users/abdulove-mng/projects/1

Для каждой задачи:

1. Задача есть в **Issues** на GitHub и привязана к **Milestone** (этапу из [roadmap.md](roadmap.md)). Нет задачи — сначала создаём.
2. `git switch main && git pull` — начинаем со свежего `main`.
3. Новая ветка: `feature/<номер-issue>-<кратко>` (для документов — `docs/…`, для исправлений — `fix/…`).
4. Коммиты маленькие и осмысленные, в формате **Conventional Commits** на русском:
   `feat: экран списка глав`, `fix: позиция чтения не сбрасывается`, `docs: …`, `chore: …`, `refactor: …`, `test: …`.
5. `git push -u origin <ветка>` → `gh pr create` с описанием «что сделано / как проверить» и строкой `Closes #N`.
6. Владелец смотрит дифф на GitHub, после его «ок» — `gh pr merge --squash --delete-branch`.
7. `git switch main && git pull`.
8. Конец этапа — тег `vX.Y.Z` и GitHub Release.

Никогда: коммитить прямо в `main`, делать `git push --force` в `main`, мержить без согласия владельца.

## Безопасность

- В git **никогда** не попадают: `.env`, пароли, ключи API, ключ подписи APK (`*.jks`, `*.keystore`), база `*.db`,
  PDF книги. Всё это — в `.gitignore`. Для настроек есть `.env.example` без реальных значений.
- Перед каждым коммитом — `git status` и взгляд на список файлов.
- Все изменяющие роуты API — только через `requireAdmin`. Секрет JWT — только из `.env`, без значения по умолчанию в коде.
